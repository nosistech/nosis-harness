# NOSIS HARNESS — Lens F: Security & Auditability (research findings, 2026-07)

Analyst: Fable 5 research pass. Date: 2026-07-17. Scope: nh-vault / nh-law / nh-tools / nh-mcp / nh-fleet hardening, judged against THE LAW (small, simple, secure, safe, lightweight, readable, auditable, modular, congruent, harmonic).

## Repo grounding (what exists today)

- **nh-vault** (`crates/nh-vault/src/lib.rs`): `KeyringVault` over the `keyring` crate (Windows Credential Manager / DPAPI), `EnvFallbackVault` (`NH_<ENTRY>_KEY`), `Zeroizing<String>` values, a `Scrubber` that redacts three shapes (`sk-`, `csk-`, JWT `eyJ…`) plus literal loaded secrets, and `sanitize_line` (control-char escaping + 500-char truncation) for terminal-spoof defense. Solid M1 baseline.
- **nh-law** (`crates/nh-law/src/lib.rs`): compiled session policy — `write_verdict` (block > ask > auto > autonomy default), `exec_verdict` (block or Ask, **never** auto-allow), repo law cannot raise autonomy (`repo_tries_to_weaken`, line 293), bundled protected paths `.git/** .nosis/** **/*.pem **/*.key **/id_rsa* **/.env*` (bundled_law test, lines 848-877). **Write-only**: there is no `[read]` rule class.
- **nh-tools** (`crates/nh-tools/src/lib.rs`): `ReadFile` (line 154) resolves paths inside the workdir but **never consults `ctx.guard`** — only `EditFile` and `ExecShell` do. `ExecShell` (line 244) strips `NH_*_KEY` env vars from the child (lines 288-293) but otherwise inherits the full parent environment and runs unsandboxed via `cmd /C`.
- **nh-tools/src/mcp.rs**: stateless 2026-07-28 MCP client. Trust dial (`auto|ask|block`), read-only annotation honored only for skipping approval on `auto` (line 632), outbound header lint against the Akamai `Mcp-*` leak vector (line 541), OAuth2 refresh-token flow with `client_secret` + refresh token in vault (`refresh_oauth`, line 412) — **no RFC 8707 `resource` parameter**, no PKCE/auth-code path. Tool descriptions from `tools/list` flow into `ToolSpec` **verbatim** (lines 611-617) and there is **no pinning**: a server can silently change a tool's description/schema between sessions or even between TTL refreshes.
- **nh-mcp** (`crates/nh-mcp/src/lib.rs`): inbound stateless server, hard-binds 127.0.0.1 (line 98) — good — but `authorized()` (line 189) **returns true for every request when no token is configured**, and there is no Origin/Host header validation. Exposes state-mutating `fleet_run`.
- **nh-fleet** (`crates/nh-fleet/src/lib.rs`): append-only `ledger.jsonl` through one mutex-guarded `DurableWriter` that fsyncs per event and scrubs via `Scrubber` — but events are **not hash-chained**; any line can be edited after the fact without detection. Receipts land in `.nosis/receipts.jsonl`.
- **Workspace** (`Cargo.toml`): lean dep set (reqwest/rustls, keyring, zeroize, regex, ratatui…), `Cargo.lock` committed. **No `deny.toml`, no cargo-audit/cargo-deny/cargo-vet anywhere in the repo, no CI security gate.**

## Threat landscape (current, cited)

- **Lethal Trifecta is now the dominant production failure mode.** Simon Willison's framing (private data + untrusted content + exfiltration channel) [simonwillison.net](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/) is echoed by OWASP's 2026 data: prompt injection still drives most agentic AI security failures in production, and coding agents are the largest tracked category (28 of 53 projects) [helpnetsecurity.com](https://www.helpnetsecurity.com/2026/06/11/owasp-prompt-injection-ai-security-failures/). Early-2026 saw a burst of production trifecta exploits within days of each other [airia.com](https://airia.com/ai-security-in-2026-prompt-injection-the-lethal-trifecta-and-how-to-defend/); Sophos frames the mitigation as *blast-radius reduction*: no execution path should hold all three legs [sophos.com](https://www.sophos.com/en-us/blog/inside-the-lethal-trifecta-blast-radius-reduction-in-ai-agent-deployments). The consensus fix is architectural (least privilege, default-deny egress, separating read-untrusted from act-privileged), not prompt-level.
- **MCP tool poisoning + rug pulls.** Hidden instructions in tool descriptions (Invariant Labs) [invariantlabs.ai](https://invariantlabs.ai/blog/mcp-security-notification-tool-poisoning-attacks); the rug-pull variant — tool definition silently changes *after* approval — got a CVE (CVE-2025-54136) [practical-devsecops.com](https://www.practical-devsecops.com/glossary/rug-pull-attack-in-mcp/). The one control that actually stops rug pulls is Trail-of-Bits-style **trust-on-first-use pinning**: hash the description at first approval, re-prompt if it ever changes; mcp-scan and multiple 2026 clients now do exactly this [mcpplaygroundonline.com](https://mcpplaygroundonline.com/blog/mcp-security-tool-poisoning-owasp-top-10-mcp-scan), [pipelab.org](https://pipelab.org/blog/state-of-mcp-security-2026/).
- **ANSI/invisible-character deception in MCP.** Trail of Bits demonstrated hiding malicious instructions in tool descriptions/outputs with ANSI escapes (tested against Claude Code, which did no filtering) [blog.trailofbits.com](https://blog.trailofbits.com/2025/04/29/deceiving-users-with-ansi-terminal-codes-in-mcp/); the original Terminal DiLLMa attack showed LLM output hijacking terminals (clipboard write, data leak, DoS via repeat codes) [embracethered.com](https://embracethered.com/blog/posts/2024/terminal-dillmas-prompt-injection-ansi-sequences/).
- **MCP authorization has converged on OAuth 2.1 + RFC 8707.** The MCP spec now REQUIRES clients to send the `resource` parameter (canonical MCP-server URI) in authorization AND token requests so tokens are audience-bound and a malicious server cannot replay a token elsewhere [modelcontextprotocol.io](https://modelcontextprotocol.io/specification/draft/basic/authorization), [den.dev](https://den.dev/blog/mcp-authorization-resource/); it became mandatory in the 2026 spec line and enterprise adoption is ~86% [dasroot.net](https://dasroot.net/posts/2026/04/mcp-authorization-specification-oauth-2-1-resource-indicators/).
- **Windows agent sandboxing matured in 2026.** OpenAI shipped a native Codex Windows sandbox built on **write-restricted tokens + synthetic SIDs** (they evaluated and rejected AppContainer as wrong-shaped for open-ended dev workflows), plus firewall-based network control [openai.com](https://openai.com/index/building-codex-windows-sandbox/), deep-dive [codex.danielvaughan.com](https://codex.danielvaughan.com/2026/05/14/codex-cli-windows-sandbox-engineering-restricted-tokens-acls-elevated-architecture/). Anthropic open-sourced `sandbox-runtime` (bubblewrap/seatbelt; filesystem + network isolation; cut permission prompts 84% internally) [anthropic.com](https://www.anthropic.com/engineering/claude-code-sandboxing), [github.com](https://github.com/anthropic-experimental/sandbox-runtime) — notably it does NOT cover Windows natively, which is NOSIS's chance to differentiate.
- **Rust supply chain is under active attack.** RUSTSEC-2026-0155: malicious crate `exploration 0.1.0` with RCE payload, live ~5 weeks before detection (July 2026) [dailycve.com](https://dailycve.com/rust-cratesio-malicious-code-supply-chain-attack-rustsec-2026-0155-critical-dc-jul2026-870/); CVE-2026-33056 in Cargo's tar handling (March 2026) [blog.rust-lang.org](https://blog.rust-lang.org/2026/03/21/cve-2026-33056/). Standard 2026 hygiene = cargo-audit (RustSec DB) + cargo-deny (advisories/licenses/bans/sources) in CI, cargo-vet for human-reviewed audits [systemshardening.com](https://www.systemshardening.com/articles/cicd/rust-cargo-supply-chain-security/), [microsoft.github.io](https://microsoft.github.io/RustTraining/engineering-book/ch06-dependency-management-and-supply-chain-s.html).
- **Infostealers now target AI-CLI users specifically.** March-2026 EclecticIQ campaign: SEO-poisoned fake Gemini CLI / Claude Code install pages delivering in-memory PowerShell infostealers that harvest OAuth tokens, DPAPI-protected data, and CI/CD creds on Windows [blog.eclecticiq.com](https://blog.eclecticiq.com/seo-poisoning-campaign-leverages-gemini-and-claude-code-impersonation-to-deliver-infostealer). DPAPI/Credential Manager secrets are readable by any same-user process [hacktricks.wiki](https://hacktricks.wiki/en/windows-hardening/windows-local-privilege-escalation/dpapi-extracting-passwords.html) — the vault protects at rest and against other users, not against same-user malware; the honest mitigation is minimizing env-var exposure + audit trails, not pretending the keyring is a HSM.
- **Tamper-evident agent audit logs are becoming a norm.** Hash-chained JSONL receipts (SHA-256 `prev_hash` per record; optionally Ed25519-signed) are the 2026 pattern for agent accountability — halo-record [github.com](https://github.com/bkuan001/halo-record), PipeLab signed agent receipts [pipelab.org](https://pipelab.org/learn/agent-action-receipts/), HMAC hash-chain how-to [tracehold.ai](https://tracehold.ai/blog/immutable-audit-log-hmac-hash-chain/).

## FINDINGS (ranked)

### F1. Pin MCP tool definitions on first approval (TOFU hash) — kill the rug pull
**Value: high / Effort: S / Scope: in / Key: none**
Today `mcp_tools()` (nh-tools/src/mcp.rs:577) rebuilds adapters from whatever `tools/list` returns; the TTL cache means a server can legally change a tool's description/schema mid-session, and nothing notices. This is exactly CVE-2025-54136's rug pull, and TOFU pinning is the acknowledged fix (Trail of Bits; mcp-scan does it).
**Design**: in `nh-tools/mcp.rs`, after `parse_tool`, compute `sha256(name + "\0" + description + "\0" + canonical_json(input_schema))` (add `sha2` — small, pure-Rust, already transitively common). Store pins in `.nosis/mcp-pins.toml` (`[server.tool] hash = "…"`), written on first listing. On mismatch: demote the tool to `McpTrust::Ask` with a one-line diff notice in the approval prompt ("tool definition changed since last approval"), and refresh the pin only on user approval. `.nosis/**` is already write-blocked by bundled law, so the model cannot edit its own pins.
**LAW fit**: secure, safe, auditable, small (one file, one hash fn). No tension.
**Evidence**: https://www.practical-devsecops.com/glossary/rug-pull-attack-in-mcp/ ; https://invariantlabs.ai/blog/mcp-security-notification-tool-poisoning-attacks ; https://mcpplaygroundonline.com/blog/mcp-security-tool-poisoning-owasp-top-10-mcp-scan ; repo: crates/nh-tools/src/mcp.rs:577-643.

### F2. Give `read_file` a guard: a `[read]` rule class in nh-law (close trifecta leg 1)
**Value: high / Effort: S / Scope: in / Key: none**
`ReadFile::execute` (nh-tools/src/lib.rs:172-180) never calls `ctx.guard` — only writes and exec are gated. So an injected instruction from any MCP tool output can have the model `read_file` a `.env`, `id_rsa`, or `*.pem` inside the workdir, and the contents flow straight into the next provider request (DeepSeek/Kimi/MiMo) — private data + untrusted content + the provider API itself as the exfiltration channel. The bundled law already blocks *writing* those globs; reading them is the more dangerous direction for secrets.
**Design**: add `Access::Read(&str)` in nh-tools and a `[read] block` list in nh-law's `LawFile`/`compile_policy`, defaulting to the same secret globs the write-block uses (`**/.env*`, `**/*.pem`, `**/*.key`, `**/id_rsa*`, `.nosis/**`). `Policy::read_verdict()` mirrors `write_verdict` minus the ask tier (block or allow — keep it simple). Blocked reads return the Ok-shaped `"blocked by law: …"` the model can adapt to. ~60 lines + tests.
**LAW fit**: secure, safe, congruent (mirrors existing verdict machinery), small. No tension.
**Evidence**: https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/ ; https://www.sophos.com/en-us/blog/inside-the-lethal-trifecta-blast-radius-reduction-in-ai-agent-deployments ; repo: crates/nh-tools/src/lib.rs:172-180 (no guard), crates/nh-law/src/lib.rs:848-877 (write-only bundled blocks).

### F3. Supply-chain gate: `deny.toml` + cargo-deny/cargo-audit in CI, today
**Value: high / Effort: S / Scope: in / Key: none**
The workspace has zero supply-chain tooling (no deny.toml, no audit config, no CI security job) while crates.io is being actively attacked: RUSTSEC-2026-0155 (malicious crate, CVSS ~9.8, live for weeks, July 2026) and CVE-2026-33056 in Cargo itself (March 2026). A harness whose brand is "constitution-native + auditable" cannot ship with an unvetted dep tree.
**Design**: (1) add `deny.toml` at repo root — advisories = deny on high/critical, licenses = allow MIT/Apache-2.0/BSD/ISC/Unicode, `sources` = crates.io only, `bans.multiple-versions = warn`; (2) a GitHub Actions job (or pre-push script, Windows-first) running `cargo deny check` + `cargo audit`; (3) commit policy: any new dependency needs a one-line justification in the PR (matches AGENTS.md gate culture). cargo-vet is deferred — heavier process, one-person team; note it as the M6+ escalation.
**LAW fit**: secure, auditable, lightweight (config + CI only, no runtime code). No tension.
**Evidence**: https://dailycve.com/rust-cratesio-malicious-code-supply-chain-attack-rustsec-2026-0155-critical-dc-jul2026-870/ ; https://blog.rust-lang.org/2026/03/21/cve-2026-33056/ ; https://www.systemshardening.com/articles/cicd/rust-cargo-supply-chain-security/ ; repo: Cargo.toml (no deny.toml in tree, Glob confirmed).

### F4. nh-mcp inbound: token required by default + Origin/Host validation
**Value: high / Effort: S / Scope: in / Key: none**
`authorized()` (nh-mcp/src/lib.rs:189-198) returns `true` for **every** request when no token is configured, and `handle()` never checks `Origin`/`Host`. 127.0.0.1 binding (line 98) is good but insufficient: (a) any other same-machine process or user session can POST `fleet_run` (state-mutating, spawns agent runs = money + code changes); (b) a browser tab can hit localhost via DNS-rebinding since the server never validates Host/Origin — the MCP spec explicitly tells local Streamable-HTTP servers to validate Origin for this reason.
**Design**: in `bind()`, when `config.token` is `None`, generate a random 32-byte token (`getrandom` is already in the tree via keyring/reqwest deps, or use `std::random` once stable; else a tiny `rand` dep), print it once in the banner as the connect instruction, and require it. Add to `handle()`: reject requests whose `Host` isn't `127.0.0.1:<port>`/`localhost:<port>` and whose `Origin` (if present) isn't a localhost origin — ~15 lines. `--token-file`/`--insecure-no-token` escape hatch for tests.
**LAW fit**: secure, safe, small. Slight UX friction (copying a token) — mitigated by printing the exact `.nosis/mcp.toml` snippet to paste.
**Evidence**: https://modelcontextprotocol.io/specification/draft/basic/authorization (auth expectations) ; DNS-rebinding rationale in MCP transport security guidance referenced by the spec ; repo: crates/nh-mcp/src/lib.rs:97-108, 135-198.

### F5. Windows-native sandbox tier for exec_shell (Job Object + write-restricted token + no-network)
**Value: high / Effort: L / Scope: in / Key: none**
Exec today is approval-gated but unconfined: an approved `cmd /C` inherits the full user token, full filesystem, and full network. 2026 practice from both major CLIs is OS-level confinement: Codex's Windows sandbox uses **write-restricted tokens with synthetic SIDs** (AppContainer was evaluated and rejected as wrong-shaped for dev workflows) + firewall-based egress control; Anthropic's open `sandbox-runtime` proves fs+network isolation cuts approval prompts 84% — but covers only Linux/macOS, leaving **Windows-first sandboxing as a genuine NOSIS differentiator** (fixes approval fatigue, differentiator #6, by making "auto" safe).
**Design**: new tiny crate `nh-sandbox` (windows-only cfg; `windows-sys` dep, no framework). Tier ladder in law: `sandbox = "none" | "jail"`. MVP "jail": (1) `CreateRestrictedToken(WRITE_RESTRICTED)` with a synthetic restricted SID granted write only on the workdir + %TEMP%; (2) assign the child to a Job Object (`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, process-count + memory caps — also fixes zombie processes, a documented Windows CLI pain); (3) network default-deny for tier-jail via a WFP/firewall rule scoped to the job or, MVP-simpler, refuse `curl|wget|Invoke-WebRequest|ssh` first tokens under jail and leave real egress filtering to tier 2. Law hook: `exec_verdict` returns `Ask` today; add `AllowJailed` so `[exec] auto_jailed = ["cargo *", "git status", …]` runs without a prompt but inside the jail — approval fatigue drops with an OS boundary, not model trust.
**LAW fit**: secure, safe, modular (own crate), harmonic with differentiator #6. Tension: not small — hence tiered, opt-in, and Windows-only first; the MVP (job object + restricted token, no firewall) is ~400 lines.
**Evidence**: https://openai.com/index/building-codex-windows-sandbox/ ; https://codex.danielvaughan.com/2026/05/14/codex-cli-windows-sandbox-engineering-restricted-tokens-acls-elevated-architecture/ ; https://www.anthropic.com/engineering/claude-code-sandboxing ; https://github.com/anthropic-experimental/sandbox-runtime ; repo: crates/nh-tools/src/lib.rs:276-306.

### F6. Hash-chain the ledger + receipts; add `nh verify`
**Value: med-high / Effort: M / Scope: in / Key: none**
The fleet ledger is append-only *by convention* (single `DurableWriter`, fsync per event) but not tamper-evident: any line in `ledger.jsonl`/`receipts.jsonl` can be edited or deleted afterwards and nothing can tell. 2026 agent-governance practice is SHA-256 hash-chained JSONL records (halo-record, PipeLab signed receipts, OpenFang) so any modification breaks every subsequent record. For a harness whose pitch is "every risky action auditable", verifiability is the missing half of auditability.
**Design**: in `DurableWriter::append` (nh-fleet/src/lib.rs:676), wrap each event as `{"seq": n, "prev": "<hex sha256 of previous line>", "event": {...}}`; genesis uses `prev = sha256(run_id)`. Same envelope for `ReceiptWriter` in nh-core. New `nh verify [run-id]` walks the chain and prints `ledger OK (412 events)` or the first broken seq. `sha2` only; no signatures in v1 (Ed25519 signing is the out-justified escalation if NOSIS ever needs third-party attestation).
**LAW fit**: auditable (its literal definition), small-ish, congruent with the existing single-writer design. Minor tension with simple — the envelope changes the JSONL shape; do it before external consumers exist (now).
**Evidence**: https://github.com/bkuan001/halo-record ; https://pipelab.org/learn/agent-action-receipts/ ; https://tracehold.ai/blog/immutable-audit-log-hmac-hash-chain/ ; repo: crates/nh-fleet/src/lib.rs:3-4, 660-690.

### F7. OAuth for MCP: add RFC 8707 `resource` parameter now; PKCE auth-code later
**Value: med / Effort: S / Scope: in / Key: none**
Slice D's `refresh_oauth()` (nh-tools/src/mcp.rs:412-485) sends `grant_type=refresh_token` + `client_id` + `client_secret` + optional `scope` — but **no `resource` parameter**. The MCP authorization spec now REQUIRES clients to include `resource=<canonical MCP server URI>` in token requests so the issued token is audience-bound; without it, a compromised/malicious MCP server can replay NOSIS's token against other services sharing the same authorization server (token mis-redemption). Also, storing a long-lived `client_secret` + refresh token makes NOSIS a confidential client by hand; the spec's preferred public-client path is authorization-code + PKCE.
**Design**: (1) MVP, ~5 lines: `form.push(("resource", self.config.url.trim_end_matches('/')))` in `refresh_oauth`, plus a contract test asserting the mock token server saw it. (2) Later slice (M): `nh mcp login <server>` doing auth-code+PKCE with a loopback redirect (reuse the tiny_http dep already in-tree for the one-shot redirect listener), storing only the refresh token in vault and dropping `client_secret` for servers that support public clients.
**LAW fit**: secure, congruent (keeps the single `request_headers` choke point), small for the MVP. No tension.
**Evidence**: https://modelcontextprotocol.io/specification/draft/basic/authorization ; https://den.dev/blog/mcp-authorization-resource/ ; https://dasroot.net/posts/2026/04/mcp-authorization-specification-oauth-2-1-resource-indicators/ ; repo: crates/nh-tools/src/mcp.rs:445-454.

### F8. Widen Scrubber shapes + preload every vault literal at session start
**Value: med / Effort: S / Scope: in / Key: none**
`KEY_SHAPES` (nh-vault/src/lib.rs:85-89) covers `sk-`/`csk-`/JWT. DeepSeek and Moonshot/Kimi keys are `sk-` shaped, but the harness routinely *touches other people's secrets*: `read_file`/exec output in any real repo will contain GitHub PATs (`ghp_`, `github_pat_`), Google (`AIza`), AWS (`AKIA`), Slack (`xox[bpars]-`), npm (`npm_`), GitLab (`glpat-`) tokens — none of which the scrubber recognizes, so they pass into logs, receipts, and the TUI verbatim. Also verify the MiMo key shape empirically and add it if it isn't `sk-` prefixed. Second gap: `Scrubber::new(literals)` is only as good as the literals the caller loads; ensure every session constructs it from **all** vault entries in the catalog (not just the routed provider) so a Kimi key echoed while running on DeepSeek still redacts.
**Design**: extend `KEY_SHAPES` with the ~7 gitleaks-style high-precision prefixes above (prefix + charset + min length keeps false positives near zero; the existing `scrub_leaves_normal_text_alone` test guards regressions). Add a `Scrubber::from_vault(entries)` helper used by nh-cli/nh-tui/nh-fleet session setup. ~30 lines + tests.
**LAW fit**: secure, small, congruent (one regex, one source of truth — `looks_like_secret` in mcp.rs inherits it for free, strengthening the header lint too).
**Evidence**: gitleaks-style pattern practice per https://zeltser.com/securing-api-keys-on-your-workstation ; leak-vector context https://blog.eclecticiq.com/seo-poisoning-campaign-leverages-gemini-and-claude-code-impersonation-to-deliver-infostealer ; repo: crates/nh-vault/src/lib.rs:85-116, crates/nh-tools/src/mcp.rs:557-562.

### F9. Sanitize MCP tool descriptions and outputs for ANSI + invisible Unicode before the model sees them
**Value: med / Effort: S / Scope: in / Key: none**
`sanitize_line` protects the *display* path, but MCP tool **descriptions** flow into `ToolSpec.description` (mcp.rs:615) and thence into every provider request unfiltered, and `call_tool` text goes to the model raw (by design, "data not instructions" — but that covers *authority*, not *stealth*). Trail of Bits showed ANSI escapes and invisible characters in descriptions/outputs hide injected instructions from the human while the model reads them fine — the user approves a tool whose visible description is benign. Claude Code shipped with zero filtering here; NOSIS can be better with ~30 lines.
**Design**: in `parse_tool` and `render_content` (nh-tools/src/mcp.rs), strip/escape: C0/C1 control chars (reuse the `escape_debug` approach from `sanitize_line`), Unicode Tags block (U+E0000–E007F — the classic "invisible prompt" carrier), zero-width chars (U+200B/C/D, U+2060, U+FEFF), and cap description length (e.g. 1,000 chars, marker appended). Keep it in nh-vault as `sanitize_untrusted_text()` so TUI, receipts, and the model-bound path share one function.
**LAW fit**: secure, small, congruent (extends existing sanitize machinery). No tension.
**Evidence**: https://blog.trailofbits.com/2025/04/29/deceiving-users-with-ansi-terminal-codes-in-mcp/ ; https://embracethered.com/blog/posts/2024/terminal-dillmas-prompt-injection-ansi-sequences/ ; https://vulnerablemcp.info/vuln/ansi-terminal-code-deception.html ; repo: crates/nh-tools/src/mcp.rs:493-536, crates/nh-vault/src/lib.rs:121-137.

### F10. Minimal-env exec: pass an allowlisted environment to children, not the full parent env
**Value: med / Effort: S / Scope: in / Key: none**
`ExecShell` removes only `NH_*_KEY` vars (nh-tools/src/lib.rs:288-293); everything else the user has in their shell — `OPENAI_API_KEY`, `GITHUB_TOKEN`, `AWS_*`, corporate VPN vars — is inherited by every approved command. One injected `set` / `env` (an innocuous-looking command a fatigued user approves) dumps them into tool output headed for a third-party model API. The 2026 trifecta guidance is least-privilege by default; Codex's sandbox similarly isolates credentials (DPAPI credential isolation in elevated mode).
**Design**: flip from denylist to allowlist: `cmd.env_clear()` then copy `PATH, SYSTEMROOT, COMSPEC, TEMP, TMP, USERPROFILE, HOME, PATHEXT, PROCESSOR_*, NUMBER_OF_PROCESSORS, LANG, TERM` (+ a law-configurable `[exec] env_allow = [...]` for project needs like `CARGO_HOME`). ~25 lines; the existing `exec_child_never_sees_nh_key_env_fallback` test generalizes to "child sees only the allowlist".
**LAW fit**: secure, safe, small, simple. Minor compat risk (builds needing odd env vars) — solved by the law-file allowlist, congruent with existing law patterns.
**Evidence**: https://www.sophos.com/en-us/blog/inside-the-lethal-trifecta-blast-radius-reduction-in-ai-agent-deployments ; https://codex.danielvaughan.com/2026/05/14/codex-cli-windows-sandbox-engineering-restricted-tokens-acls-elevated-architecture/ (credential isolation) ; repo: crates/nh-tools/src/lib.rs:285-293.

### F11. `nh key doctor` — surface the same-user-malware reality honestly
**Value: low-med / Effort: S / Scope: out-justified (UX + security posture) / Key: none**
The vault story is strong at rest, but DPAPI/Credential Manager secrets are readable by any process in the same user session (HackTricks documents turnkey extraction), and infostealers are now specifically targeting AI-CLI users on Windows (EclecticIQ, March 2026: fake Gemini CLI/Claude Code installers, in-memory PowerShell, DPAPI harvesting). NOSIS can't fix same-user malware, but it can stop *making it worse* and tell the user the truth.
**Design**: `nh key doctor` (nh-cli): (a) warns for each `NH_*_KEY` env var that is set **persistently** (check `HKCU\Environment` on Windows) — persistent env vars are the softest target and the vault makes them unnecessary; (b) lists vault entries with last-used timestamps from receipts; (c) prints a 3-line threat-model note ("vault protects at rest and from other users; nothing protects from malware running as you — see receipts for every key use"). Also: record `key_source: keyring|env` per receipt so audits show when the weaker path was used. ~100 lines, no deps.
**LAW fit**: secure, auditable, readable (honest UX beats false assurance — congruent with the honest-identity principle already in the harness). No tension.
