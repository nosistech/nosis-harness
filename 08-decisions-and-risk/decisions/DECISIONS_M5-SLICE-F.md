## 2026-07-20: W5 — "Never fabricate unmetered": a receipt without usage adds ZERO tokens to the budget, loudly
**Decision:** When a fleet task's receipt comes back with `usage: None`, nosis adds nothing to `used_tokens`. Instead it (a) emits a one-line warning "usage unreported — budget cannot count this task" whenever a budget is set, and (b) surfaces a durable, poll-visible `unmetered` count in `FleetStatus` and the nh-mcp `fleet_status` render (`· N unmetered`). No estimate is ever invented.
**Alternatives considered:**
- Warn + add an ESTIMATE to `used_tokens` — explicitly rejected in the amendment: "No estimate is ever added to `used_tokens` — inventing un-billed tokens is the meter lying upward, exactly what W3 refused (a real currency hard-stop is M6). Rejected: warn + estimate." (CONTRACTS_M5.md §8, A-M5-8 design call 3.)
**Why:** This is the product thesis applied against itself. The meter must not lie *in either direction* (BUILD_LOG W3 entry: "the meter must not lie, in EITHER direction") — fabricating consumption to make a budget look enforced is as dishonest as hiding spend. The honest posture is: count what you can prove, and *show* what you couldn't count. Serves THE LAW's *auditable* and *congruent* (the fleet now treats missing usage the same way W3's `cache_hit_pct` treats impossible cache math: return honesty, not a guess). Fixes audit finding low-25 (receipts-without-usage never trip the budget — silently).
**Immediate effect on the harness:** `FleetStatus` gained `unmetered: usize`; `execute_tasks` warns per unreported receipt; `tokens_in(usage=None)==0` verified by a dedicated test in the adversarial review. The trade is explicit: a provider that never reports usage can spend past a token budget — but the user is told, per task, that the budget cannot count it.
**Long-term consequence:** Forecloses any future "estimated tokens" creeping into billing-adjacent numbers; the amendment names the real fix (a currency hard-stop) as M6 work. Establishes `unmetered` as a first-class honesty channel that later surfaces (MCP `fleet_status`) render.
**Evidence:** Commit `eaadfb2` body ("A receipt with usage=None contributes zero tokens (never fabricated)…"); CONTRACTS_M5.md §8 A-M5-8 design call 3 (owner-ratified, with the rejected alternative named); audit low-25; W5 items W5-9/W5-11 in §0.1-F; gate 410/0/1; review check "`tokens_in(usage=None)==0` (no fabricated tokens)" (BUILD_LOG 2026-07-20 W5 entry).
**Article angle:** When a provider doesn't report token usage, the harness refuses to invent a number for its own budget — it counts zero and tells you what it couldn't count.
**Review later:** yes — trigger: M6's currency hard-stop, which is the named real fix for budget enforcement under unreported usage.

## 2026-07-20: W5 — std `File::try_lock` as the PRIMARY single-writer fleet lock (not a heartbeat)
**Decision:** One coordinator per run, enforced by an OS advisory lock on a dedicated `<run_dir>/coordinator.lock` via std's `File::try_lock`, held RAII-style for the coordinator's lifetime. `run`/`run_with_id` fail fast on contention; `resume` retries ~2s at 50ms intervals (absorbing Windows' documented post-termination lock-release lag) then errors "run appears live (pid N, started T)" using diagnostics stored in the lock file. The lock file is opened `truncate(false)` and only rewritten AFTER acquisition; it is left in place on drop. Index appends are serialized under a separate blocking `index.lock`. Never lock `ledger.jsonl` itself.
**Alternatives considered (all four enumerated in A-M5-8 design call 1):**
- Dep-free heartbeat-lockfile (PID + refreshed mtime + staleness steal) — rejected as primary because "any heartbeat design breaks the E1 `fleet_kill_resume` contract — that test resumes within ~1s of `kill()`, before any sane staleness threshold… would permit the steal" (CONTRACTS_M5.md §8 A-M5-8). Kept as a pre-authorized fallback contingency so Sol would never stop mid-run; the self-report had to state which path shipped — the std lock shipped (BUILD_LOG 2026-07-20: "Lock strategy shipped = std `File::try_lock` (the PRIMARY, not the heartbeat fallback)").
- `fs2` crate dependency — rejected: std file locking stabilized (Rust 1.89; workspace pinned 1.96.0, orchestrator-verified that `rustc 1.96.0` compiles `File::lock/try_lock/unlock`), so a dep buys nothing (§0.4: no new runtime crates; W5 shipped "no new deps").
- No-steal lockfile — rejected: no auto-recovery after a kill; the std lock "auto-releases when a dead process's handles close" with no staleness heuristic (A-M5-8).
- Locking `ledger.jsonl` directly — rejected: "Windows mandatory-lock semantics would break concurrent status readers" (A-M5-8).
**Why:** Dep-free (*small*, *lightweight*), OS-enforced with no staleness heuristic (*secure*, *safe*), and it preserves an existing behavioral contract (the E1 kill/resume test resumes ~1s after kill — a decisive, testable tie-breaker). Fixes audit medium-15 and is the stated foundation for high-7's readers-never-mutate fix (§0.1-F: "the lock is the foundation; high-7 repair-under-lock depends on it").
**Immediate effect on the harness:** Two coordinators can no longer corrupt one run's ledger; a killed run auto-recovers; ledger readers became pure (`fs::read` + `parse_jsonl`, torn final line tolerated in memory only), with `set_len` tail repair confined to write paths under the lock. Real Windows contention + kill/recovery integration test added (`nh-cli/tests/fleet_lock.rs`, 143 lines). `fleet_kill_resume.rs` untouched and required green.
**Long-term consequence:** Ties fleet correctness to the pinned toolchain floor (std file-lock APIs, 1.96.0). Forecloses heartbeat/staleness designs unless the E1 contract is renegotiated.
**Evidence:** Commit `eaadfb2` (W5-1/W5-1b/W5-2/W5-3); CONTRACTS_M5.md §8 A-M5-8 design call 1 (all rejected options + tie-breaker verbatim); §0.1-F W5 table; gate 410/0/1, +15 tests; BUILD_LOG 2026-07-20 W5 entry (zero-blocking review: "lock blocks a 2nd coordinator + auto-recovers on kill").
**Article angle:** The fleet's single-writer lock was chosen by a testable tie-breaker: the design that couldn't resume within one second of a kill lost.
**Review later:** no.

**Evidence:** CONTRACTS_M5.md §8 A-M5-8 (full rationale + rejected alternative + mutable-surface table); commit `eaadfb2` (W5-3/W5-4 in body); commit `e903ef0` "Deferred at the frozen boundary (owner-authorized)" paragraph; audit medium-11/high-6/medium-16/medium-17; gate 410/0/1.

## 2026-07-19: W2 — one egress choke point: every tool result passes ToolResultEnvelope (cap + real-literal scrub)
**Decision:** ALL tool output — built-in and MCP alike — egresses to the model through `ToolResultEnvelope` (32k elision cap + scrub), and the envelope now takes the session scrubber so a configured key's *exact literal* is redacted, not just sk-/csk-/JWT shapes. The three interactive callers (cmd_run, cmd_chat, nh-tui) install real key-literal scrubbers via a new `with_scrubber` builder; `ToolCtx::new`'s signature is unchanged so frozen nh-fleet takes no ripple and keeps the default shape-only scrubber.
**Alternatives considered:**
- Changing `ToolCtx::new`'s signature — avoided by design: "W2-4's `scrubber` field is added WITHOUT touching `ToolCtx::new`'s signature" because nh-fleet builds `ToolCtx` via `new(...).with_guard(...)` (CONTRACTS_M5.md §0.1-F W2 header, frozen-safe verification). No other alternative is recorded.
**Why:** Audit high-3: MCP results bypassed the envelope entirely — a hostile or verbose server could inject unbounded bytes into paid context (against the metered thesis) and secret-shaped strings went to the provider unredacted while identical read_file output was `[REDACTED]`. One choke point restores *congruent* treatment of both tool families and serves *secure*/*small* (a single path to `render()`, verified in review).
**Immediate effect on the harness:** MCP output is bounded + scrubbed like everything else; read_file and each exec stream additionally bounded to 2 MiB pre-envelope (W2-9, OOM guard).
**Long-term consequence:** "The single egress cap+scrub choke point for all tools" becomes an invariant later waves extend (Slice G's scrubber work modifies this one point rather than hunting call sites).
**Evidence:** Commit `e903ef0` (W2-1 high-3, W2-4 medium-5, W2-9; review: "the egress choke point is the only path to `render()`"); audit high-3 verifier text; gate 395/0/1, +18 tests.

## 2026-07-19: W2 — CSPRNG bearer token + constant-time compare via vetted crates, not hand-rolled
**Decision:** The loopback MCP server's auth token is minted from the OS CSPRNG (`getrandom`, 32 bytes → 64 hex) instead of std SipHash, and the bearer is compared in constant time (`subtle::ConstantTimeEq`, with a length guard so ct-compare only runs on equal-length input). Two new direct deps (`getrandom`, `subtle`) accepted as a scoped exception to "no new runtime crates" because both were already compiled transitively — zero build weight.
**Alternatives considered:**
- Hand-rolled randomness / manual byte-loop compare — rejected in the ratified call: "use `getrandom` (CSPRNG token) + `subtle` (constant-time bearer) — vetted primitives over hand-rolled crypto" (BUILD_LOG W2 entry, ratified call 2).
- Keeping the "no new runtime crates" rule absolute — overridden narrowly, same pattern as W1's `url` exception: "both already transitive → §0.4" (CONTRACTS_M5.md §0.1-F W2 header; §0.4 "Slice F W2 exception (owner-ratified 2026-07-19)").
**Why:** Audit low-17 (SipHash token is not cryptographic) + low-19 (early-exit compare leaks timing). *Secure* over *small* — but only barely, since the dependency cost was already paid transitively. Accompanied by W2-14 (1 MiB body cap → 413) and W2-18 (exact-match routing, else 404): the whole preview server's inbound surface hardened together.
**Immediate effect on the harness:** Real auth on the 127.0.0.1 preview server; Cargo.lock gained exactly two edges. Later live-verified: no-bearer → HTTP 401 (CURRENT_TASK.md session-2 checkpoint, MCP live-verify).
**Long-term consequence:** Established the template for dependency exceptions: owner-ratified, security-critical seam, already-transitive-only. (Slice G later hardened this further — caller tokens ≥32 bytes — building on, not replacing, this primitive choice.)
**Evidence:** Commit `e903ef0` (W2-11/W2-13; getrandom 0.2.17 + subtle 2.6.1); CONTRACTS_M5.md §0.4 W2 exception + §0.1-F ratified call (2); audit low-17/low-19; gate 395/0/1.
**Article angle:** Even a localhost-only preview server got a cryptographic token and constant-time auth, imported rather than improvised.
**Review later:** no.

## 2026-07-19: W2 — dependency-free 300s exec timeout, null stdin, whole-tree kill; exec runs the approved bytes VERBATIM
**Decision:** `ExecShell` can no longer hang a session: null stdin, stdout/stderr drained on dedicated threads (no pipe-buffer deadlock), a 300-second deadline, and on timeout a whole-process-tree kill (`taskkill /T` on Windows, kill-process-group on Unix) returning an Ok-shaped "timed out … killed" result. Built with std only — no async runtime, no timeout crate. Separately (same wave, same ratification batch): on Windows the approved command is passed to `cmd /C` via `raw_arg`, so the bytes the user approved are the bytes executed — std's MSVC argv re-quoting had been mangling any command containing double quotes (e.g. `git commit -m "two words"`).
**Alternatives considered:**
- A timeout/async dependency — the ratified call specifies "dep-free exec timeout, 300s, null stdin" (BUILD_LOG W2 ratified call 4; CONTRACTS_M5.md §0.1-F call (4)), consistent with §0.4's no-new-runtime-crates rule. No competing design is recorded.
**Why:** Audit medium-4 (exec can hang the turn) and high-4 (Windows quoting differential: "the byte string the user approved via ctx.approve is not the byte string executed" — an approval-integrity failure on the flagship platform). Serves *safe* (bounded, killable), *lightweight* (std-only), and the approval invariant in §0.3 ("Approvals show the full action"): approval is meaningless if execution rewrites the command.
**Immediate effect on the harness:** Quoted commit messages and paths-with-spaces work correctly on Windows; a wedged child process ends the tool call at 300s with the whole tree reaped, and the model receives an honest timed-out result instead of the session hanging.
**Long-term consequence:** The exec boundary stayed dependency-free, which kept it cheap for Slice G W7 to revisit (exec approval-at-boundary + process-tree kill hardening) on the same foundations.
**Evidence:** Commit `e903ef0` (W2-2 high-4, W2-3 medium-4; review: "timeout kills the whole tree + prevents a late marker"); audit high-4 verifier (backslash-quote mangling confirmed against cmd.exe parsing); CONTRACTS_M5.md §0.1-F W2 rows W2-2/W2-3; gate 395/0/1.
**Article angle:** The harness guarantees that the exact bytes a user approves are the bytes that run, and that no command can hold the session hostage past five minutes.
**Review later:** no.

## 2026-07-19: W3 — cross-currency routing normalizes through FRESH FX only, and REFUSES on stale FX rather than guessing
**Decision:** `resolve_capable` (the "cheapest capable route" chooser) compares candidate costs natively within one currency; across currencies it normalizes to USD *only* via fresh catalog FX. When FX is stale, it REFUSES the non-comparable route with the trace reason `"fx stale"` — it will not compare ¥ against $ numerically, will not apply a cached/guessed rate, and will not silently prefer either side. The "N.Nx price" ratio in rejection traces is emitted only between same-currency pairs; cross-currency traces print both native amounts. Catalog parsing additionally rejects any provider that mixes currencies (W3-13, fail-closed at the data layer).
**Alternatives considered (from the audit's own fix menu, high-2):**
- Partition-by-currency with per-currency winners, cross-comparing only via FX — the audit offered this as option (b); the ratified call chose fresh-FX USD normalization with fail-safe refuse (CONTRACTS_M5.md §0.1-F W3 header, ratified call Q3: "high-2 normalizes cross-currency to USD via FRESH fx, fail-safe when stale").
- Raw numeric comparison (status quo) — rejected as the bug itself: a ¥3/M route (≈$0.42) numerically lost to a $2/M route; "the harness can pick a genuinely more expensive route while claiming 'cheapest capable'" (audit high-2, orchestrator spot-checked).
- Comparing via stale FX anyway — rejected implicitly and by the shipped behavior: stale FX → the route is refused as non-comparable, never priced by a guessed rate (commit `2b68163`: "REFUSES the non-comparable route (trace 'fx stale') rather than comparing ¥ against $").
**Why:** This is the core meter-honesty surface of a product whose thesis IS the honest meter. The crate already guarded every other seam (`naive_cost` filters same-currency; `provider_default` documents the assumption) — resolve_capable was "the one seam without the guard" (audit high-2 verifier). Refusing on stale data is *safe* and *auditable*: a refusal with a stated reason is checkable; a silently-converted guess is not. Congruent with Slice C's precedent (the `≈$` USD gloss is omitted when FX is stale, never FX-summed — CURRENT_TASK.md Slice C block) and later reused verbatim by the fleet's unmetered-honesty call ("exactly what W3 refused", A-M5-8).
**Immediate effect on the harness:** `nh why` / `/why` traces stopped displaying cross-currency price ratios that were numerically meaningless (the audit found deepseek-v4-flash shown as "~7.1x price" against a near-parity route). A stale-FX candidate is visibly refused rather than mispriced.
**Long-term consequence:** "Never compare, sum, or convert across currencies except through fresh FX — otherwise refuse" became a load-bearing invariant: the Release-Slice MCP tools inherited it (cross-currency-refused + usd_approx-only-on-fresh-fx were explicit review checkpoints for `1d04871`) and the live provider tests verified it against real money ("cross-currency REFUSED in `nh why` (¥-vs-$ 'not directly comparable')… no fabricated savings" — CURRENT_TASK.md session-3 checkpoint, ≈$0.0014 total real spend).
**Evidence:** Commit `2b68163` (W3-11, high-2; W3-13 nit-3); audit high-2 + its verifier paragraph; CONTRACTS_M5.md §0.1-F W3 ratified call Q3 (2026-07-19) + W3-11 row; gate 377/0/1; review check "no raw ¥-vs-$ compare + fail-safe on stale fx" (BUILD_LOG W3 entry); live verification 2026-07-20 (CURRENT_TASK.md session-3).
**Article angle:** When the exchange rate is stale, the router declines to pick a winner across currencies at all — a refusal it prints, rather than a conversion it guesses.
**Review later:** yes — trigger: any future FX-source change or a request to rank refused-for-staleness routes; the refusal semantics are now depended on by MCP tools and tests.

## 2026-07-19: W3 — DROP the compaction cost guard: overflow-avoidance beats cache warmth
**Decision:** The guard in `compact_history` requiring elided > retained tokens was deleted outright. Compaction now actually fires at the 0.70 trigger on a normal uniform-turn history, and the trigger computes `input_tokens = max(provider prompt count, fresh local estimate)` so a just-appended large tool result is seen (W3-2).
**Alternatives considered (both from the audit's fix menu, high-1):**
- Fold the cost check into candidate selection (pick the first index satisfying retained ≤ target AND elided > retained) — the audit's option (a); the ratified call chose the simpler full drop (CONTRACTS_M5.md W3-1 row: "drop the `elided<=retained` guard (compaction only runs post-trigger; overflow-avoidance beats cache-warmth)").
- Keep the guard (status quo, protecting prefix-cache warmth) — rejected because it made compaction effectively dead: at the 0.70 trigger, elided ≈ 20% vs retained ≈ 50%, so the guard "returns None on essentially every trigger" and ≤256k routes hard-fail with a provider context error before compaction ever fires (audit high-1 verifier).
**Why:** The guard optimized a secondary cost (one-time cache re-prefill) at the price of the primary failure mode (hard context overflow ending the run). The ratified rationale is one line: "avoiding a hard context overflow beats keeping the prefix cache warm" (BUILD_LOG W3 entry, ratified call high-1). Serves *simple* (delete the guard, don't engineer around it) and *safe*. A realistic uniform-turn test at limit proportions was mandated with the fix.
**Immediate effect on the harness:** Long sessions on window-sized routes stop dying with provider context errors; compaction behaves as designed at 70%.
**Long-term consequence:** Accepts an occasional cache-warmth cost as the price of session survival; any future re-introduction of a cost heuristic must beat the "compaction fires on a realistic uniform history" test added here.

## 2026-07-19: W1 — parse hosts with the `url` crate (reqwest parity), closing the `\@` credential-exfil differential

## 2026-07-19: W1 — glob matchers rewritten iteratively: no input can overflow the stack
**Decision:** nh-law's `glob_matches`/`segment_matches` were rewritten from recursion to an iterative two-pointer-with-backtrack algorithm (O(1) stack), with semantics byte-identical. A hostile path (60k segments, or a 200k-character segment) can no longer overflow the main-thread stack and abort the whole session.
**Alternatives considered:**
- Clamp oversized input to the fail-safe verdict — authorized as the drop-if-hard fallback in the seam table ("drop-if-hard: clamp oversized input to the fail-safe verdict", CONTRACTS_M5.md W1-9 row); the full iterative rewrite shipped instead, so no clamp heuristic was needed.
- Depth-limited recursion — not recorded as considered.
**Why:** Audit medium-7: the policy engine — the component deciding what a hostile repo may do — could itself be crashed by input from that repo (a stack-overflow DoS is an abort, not a catchable error). *Secure* and *safe* with zero semantic change ("semantics byte-identical", commit body): the matcher's observable behavior is preserved while the failure mode is eliminated rather than bounded.
**Immediate effect on the harness:** Law evaluation is total over arbitrary-size inputs; the fallback clamp was never exercised.
**Long-term consequence:** Sets the pattern (unbounded-recursion-on-untrusted-input is a finding class, fixed by construction) without leaving a tuning knob (no depth limit to revisit).
**Evidence:** Commit `d95a8d6` (W1-9, medium-7: "ITERATIVELY (two-pointer backtrack, O(1) stack)"); audit medium-7; CONTRACTS_M5.md §0.1-F W1-9 row; gate 363/0/1.
**Article angle:** The policy engine was made impossible to crash with a long path — by removing recursion, not by capping it.
**Review later:** no.
